# GitIgnore：干净仓库维护

## 目标

让 `.gitignore` 只排除不应进入版本库的本地状态、生成物和敏感配置，同时保留项目真正的源码、可复现配置和协作所需资产。

适用于新仓库初始化、开发过程中出现杂项文件、或用户要求审查/补齐 `.gitignore` 时。不要用它清理 Git 历史、删除文件或替代密钥管理。

## 先判断，再修改

1. 找到目标仓库根目录；如果尚未 `git init`，只创建或建议创建 `.gitignore`，不要主动初始化仓库。
2. 读取现有 `.gitignore`、`git status --short --untracked-files=all` 和已跟踪文件。保留原有注释、例外规则和项目约定，避免重复条目。
3. 扫描项目语言、构建工具、编辑器和本地目录。将发现项分为“可直接加入”“建议加入”“不能忽略”三类，并说明理由。
4. 用户明确要求创建或更新时再写入文件；若只要求审查，给出候选规则和风险，不改文件。

`.gitignore` 只影响尚未跟踪的文件。若命中规则的文件已经被跟踪，保留其跟踪状态，并单独告知用户；只有获得明确授权后，才可用 `git rm --cached` 停止跟踪。

## 默认基线

在普通代码仓库中，加入下列用户指定的本地文件与二进制交付物规则。按分类保留注释；已有等效规则时不重复添加。

```gitignore
# OS metadata
.DS_Store
Thumbs.db

# Local AI and knowledge-base state
.claude/
.codex/
.obsidian/
.obsidain/

# Local image and office deliverables
*.png
*.tif
*.tiff
*.doc
*.docx
*.docm
*.dot
*.dotx
*.dotm
```

`.obsidian/` 是标准目录名；同时保留 `.obsidain/`，以覆盖用户给出的常见拼写目录。

在加入 `*.png`、`*.tif`、`*.tiff` 或 Word 通配符前，检查这些文件是否是项目必须版本化的源素材、产品资源或文档。如果仓库确实依赖未跟踪的此类文件，先指出冲突，并建议用户选择：保留这条全局规则、改为只忽略某个输出目录，或用 `!path/to/required-file` 例外保留。已跟踪文件不自动取消跟踪。

## 项目扫描与建议

根据实际项目特征提出建议，不要把不确定的目录直接忽略。

| 发现 | 默认处理 | 典型规则 |
| --- | --- | --- |
| Node.js 依赖、构建和覆盖率输出 | 发现后可直接加入 | `node_modules/`、`dist/`、`build/`、`coverage/`、`.next/` |
| Python 虚拟环境、字节码和测试缓存 | 发现后可直接加入 | `.venv/`、`venv/`、`__pycache__/`、`*.py[cod]`、`.pytest_cache/`、`.mypy_cache/` |
| Java、Gradle、Maven、Rust、Go、C/C++ 等可再生构建物 | 发现后可直接加入 | `.gradle/`、`target/`、`bin/`、`obj/`、`cmake-build-*/` |
| IDE 和本地运行状态 | 先看项目是否共享设置，再建议 | `.idea/`、`.vscode/`、`*.swp`、`*.swo` |
| 日志、临时报告、下载、实验输出、模型检查点 | 先确认是否可再生，再建议 | `*.log`、`tmp/`、`downloads/`、`outputs/`、`checkpoints/` |
| 环境变量、私钥、令牌或本地数据库 | 立即高优先级建议，谨慎处理 | `.env`、`.env.*`、`*.pem`、`*.key`、`*.sqlite` |

对于 `.env`，使用 `.env`、`.env.*` 和 `!.env.example` 的组合，保留可提交的 `.env.example` 或同等示例文件。不要在回复、差异或命令输出中展示任何密钥内容。若敏感文件已被跟踪，说明风险和移除方案，但在用户明确同意前不要修改 Git 索引或历史。

不要默认忽略以下内容：源码目录、`src/`、`docs/`、`assets/`、依赖锁文件、`Dockerfile`、CI 配置、迁移文件、项目配置，以及无法确认是否可再生的数据。尤其不要加入过宽的 `*`、`/*`、`**/*` 或整个项目目录规则。

## 写入原则

- 将新增规则放在语义清晰的小节中；优先使用目录规则而非模糊的文件名规则。
- 先复用现有模式，避免相同规则出现在多个位置。
- 规则越窄越好：只有确定某类文件都是本地产物时，才用扩展名通配符。
- 如果项目已有来自 GitHub gitignore 模板或团队规范的规则，以现有规范为主；本 skill 的默认基线补充其缺口。
- 不删除现有规则、不改写文件格式、不使用强制 Git 命令。

## 验证与交付

修改后，检查 `.gitignore` 差异，并使用 `git check-ignore -v --no-index` 验证代表性路径能命中预期规则。再查看 `git status --short`，确认不会意外隐藏待提交源码。

交付时简洁说明：

1. 已加入的规则及对应原因；
2. 发现但未自动加入的候选项和判断依据；
3. 已跟踪文件、敏感文件或版本化素材的冲突（若有）及下一步选择。

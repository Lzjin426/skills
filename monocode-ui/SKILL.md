# MonoCode UI

把 MonoCode 当作桌面工作界面的参考案例，提炼它解决问题的规则，而非复制固定的三栏布局或颜色值。先理解目标软件里的对象、任务和操作频率，再决定界面结构。案例证据与实现边界见 [references/monocode-reference.md](references/monocode-reference.md)；需要具体布局、视觉或交互依据时再读。

## 组织工作空间

- 先列出用户反复切换的对象、需要并排比较的内容，以及必须一直可见的状态。每个常驻区域都应有明确职责。
- 多项目、多任务并行时，可用侧栏定位对象、顶部标签切换工作上下文、主区域承载实际工作；只有确有并排查看需求时才加入分屏或辅助面板。不要让侧栏标签、顶部标签和内容标签重复承担同一种导航。
- 让主要内容占据最多空间。次要信息靠近它所解释的对象；低频操作放入上下文菜单或局部工具栏，保持主工作区安静。
- 面板宽度、折叠和分屏比例按内容设定上下限。缩窄窗口时，优先收起次要区域、保住主要任务和可读性。

## 建立克制的视觉规则

- 先定义背景、表面、文字、分隔线、强调色及语义状态的设计变量，再设计具体组件。浅色与深色主题分别检查，不直接反转颜色。
- 用细分隔线、轻微明度差和留白表达层级；卡片、阴影和模糊只用于确实需要浮起或分组的内容。强调色主要留给当前选择、焦点及关键反馈。
- 用字号、字重、对比度区分主内容、说明和元数据。紧凑列表仍要让名称、状态、来源和可执行操作容易扫读；超长路径和标题要有明确截断与查看方式。
- 为选中、悬停、键盘焦点、忙碌、禁用、空白和错误状态分别设计可辨认反馈，避免只用颜色传达含义。

## 做实交互

- 标签、列表和面板的拖动或调整尺寸应有预览、边界和取消行为；操作时避免误选文字。保留用户需要的尺寸、顺序或当前上下文。
- 菜单和弹层贴近触发点，处理窗口边缘、滚动容器裁切、外部点击、Escape 和焦点返回。按钮和菜单项要有可理解的名称与键盘路径。
- 在真实内容、长标题、大量项目、空状态和处理中检查界面；精致感来自这些状态的连续性，不能只看静态首页。

## 适配平台并验收

- 先沿用目标项目的框架和组件体系；这些设计规则不要求 React、Tailwind 或 Tauri。桌面原生材质与窗口按钮可增强质感，但应按目标平台实现，并提供可读的普通背景退路。
- 交付前查看实际渲染截图：至少覆盖常规桌面宽度和较窄窗口；若产品支持多主题，分别检查。验证布局、文字对比、焦点、溢出、弹层和主要任务流，并修正发现的问题。

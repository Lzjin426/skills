# Markdown 文档写作与结构规范

这是一份与具体知识库、目录结构、插件和账号无关的 Markdown 规范。目标是让文档在阅读、迁移、合并、渲染和导出时都保持可用。唯一的例外是第四节 4.2：它记录的是用户既有的附件归置约定，属于“用户明确要求 / 项目约定”层级，换项目时按目标项目的约定替换。

规则的优先级如下：用户的明确要求，项目或仓库已有约定，目标编辑器或渲染器的实际限制，本规范的默认建议。发现目标环境有自己的规则时，先遵循目标环境，不要把本规范的默认值硬套上去。

## 一、适用范围与边界

- 管：`.md` 文件的结构、格式、链接、图片与附件引用、附件归置、公式排版、元数据和跨环境迁移。
- 不管：事实核验、论证质量、研究结论、专业内容补写，以及需要专门工具处理的云文档排版、OCR 或复杂 Office 格式。
- **只改结构与写法，不改内容事实。** 发现疑似缺段、编号跳号、前后矛盾或引用失效时，单独报告，不擅自补写、删改或改变原意。
- 默认以 CommonMark/GFM 可移植性为基线。Obsidian 的双链、Callout 和嵌入语法属于扩展，只有目标明确使用 Obsidian 或用户明确要求时才采用。

## 二、标题与文档结构

1. 独立文档通常使用一个 H1 作为文档标题；短片段、引文或单条备忘可以没有标题，但不应直接从 H2/H3 开始。
2. 标题层级必须逐级递进，不得从 H1 直接跳到 H3。标题不是为了视觉放大而随意选择层级。
3. 手工编号不是 Markdown 的必需语法。只有项目或用户要求编号时才添加；一旦采用，就要在同一文档中保持编号格式、层级和连续性一致。
4. 文件名是否作为文档标题由目标环境决定。不要因为“文件名像标题”就自动删除正文 H1，也不要在环境已经显示文件名时重复堆叠标题。
5. 标题独占一行，前后各留一个空行。标题文本应表达该节内容，不用加粗文本冒充标题。
6. 顶层章节宜围绕文档主线组织，避免制造大量只有一两行内容的浅层标题。

推荐的可移植结构：

```markdown
# 文档标题

开头用一两句话说明问题、范围或结论。

## 第一部分

正文……

### 具体问题

正文……

## 第二部分

正文……
```

如果目标项目明确要求显式编号，再按项目约定写成 `# 1. 标题`、`## 1.1 子节` 等，不要让本 skill 的默认值覆盖项目约定。

## 三、链接与引用

### 3.1 通用 Markdown 默认

1. 文档之间默认使用标准 Markdown 链接：`[显示文字](相对路径/目标.md#标题锚点)`。
2. 项目内链接优先使用相对路径，避免写入本机绝对路径、`file://` 地址或依赖某台电脑的路径。
3. 外部网页使用完整 URL；只有在目标要求离线交付或长期归档时，才考虑下载并改为本地资源。
4. 不要只写“见前文”“见第 2 节”这类依赖上下文的引用。能稳定链接时链接到目标文档或标题；不能稳定链接时用完整文字说明出处。
5. 修改标题或文件名时，要同步检查引用目标、锚点和显示文字；不要为了“看起来像链接”而制造不存在的目标。

### 3.2 Obsidian 扩展

当目标明确是 Obsidian 库时，可以使用 `[[笔记名]]`、`[[笔记名|显示文字]]` 和 `![[资源名]]`。这类写法不能默认替换普通 Markdown 链接，也不能假设所有 Markdown 阅读器都能解析。

## 四、图片与附件

### 4.1 通用默认

1. 默认使用标准 Markdown 图片语法：`![替代文字](相对路径/图片.png)`。替代文字应能说明图片内容或用途。
2. 资源目录由项目或目标工具决定，不预设目录名。没有既有约定时，选择清晰、稳定且相对于当前文档可解析的目录。
3. 需要迁移、离线阅读或导出时，优先使用项目内资源，不要依赖容易失效的远程图片或本机绝对路径。
4. 同一资源尽量只保存一份。遇到同名文件时先确认内容是否相同，不要直接覆盖。
5. Obsidian 的 `![[文件名.png]]`、Excalidraw 嵌入等只在目标环境支持时使用，并遵循该库已有的资源路径约定。

### 4.2 附件集中约定

本节是用户的既有约定，优先级高于 4.1 第 2 条的“不预设目录名”。默认适用于本人管理的 Obsidian 库；换成其他项目时按其自身约定执行。

1. **所有附件集中放在库根目录的附件文件夹**：图片、画板、PDF、表格、幻灯片、压缩包等一切非笔记文件都算附件。附件目录名以目标库的实际配置为准——Obsidian 读 `.obsidian/app.json` 的 `attachmentFolderPath`，本库为 `附件/`。动手前先确认，不要凭印象。
2. 笔记目录只放笔记，不保留 `image/`、`图/`、`assets/`、`Excalidraw/` 之类的资源子目录。笔记目录里出现的非 `.md` 文件按放错位置处理。
3. 附件目录保持扁平，不再建子目录；目标库本来就有既有的子目录约定时，随它的约定。
4. **画板（`.excalidraw.md`）算附件，不算笔记。** 判断标准是“这个文件是被别的笔记引用、嵌入的资源，还是承载知识的正文”，不是扩展名。
5. 插件可能自带独立的资源目录设置（例如 Excalidraw 插件的 `folder`），必须与核心附件目录对齐。Obsidian 运行时改插件 `data.json` 会被它回写覆盖，这类改动提示用户在插件设置界面里做，不要直接改文件。
6. 外部源材料、文献库这类本来就有独立材料目录（如项目的 `01-材料`）的内容，随项目约定，不受本节约束。

### 4.3 附件搬迁与改引用

1. 顺序固定：先搬运附件，再改引用，最后逐条验证解析。不要留下半迁移状态。
2. 集中化之后，相对路径写法 `![](子目录/图.png)` 必然失效。引用要换成与位置无关的写法：Obsidian 用 basename 双链 `![[文件名.png]]`、`![[文件名.png|题注]]`，它按文件名解析，附件集中化或笔记改名后仍然有效。
3. 由 `![题注](路径)` 改双链时，把题注搬到别名位：`![[文件.png|题注]]`。双链无法同时表达显示宽度和题注（如 `![题注|565](路径)`），必须二选一时保留题注，并在报告里说明宽度被舍弃。
4. 用脚本或 `mv` 搬动、重命名文件不会触发 Obsidian 的自动更新链接（`alwaysUpdateLinks` 只在 Obsidian 界面内改名时生效），出入链要自己查、自己改。
5. 搬之前查同名：Obsidian 按最短路径解析，重名时可能挑错文件。同名文件先比对内容，再决定去重、改名还是两份都留。
6. 搬之后做全库检查：附件目录之外不应再有媒体文件，每条引用都要能按文件名命中。缺图和孤儿附件都要在报告里写清楚，不要静默处理。

## 五、公式、代码与表格

1. 公式语法取决于目标渲染器。若目标支持 LaTeX，行内公式使用 `$...$`，行间公式使用独立成段的 `$$`；不要把 `$$` 挤进行文。
2. 行间公式建议写成：

   ```markdown
   $$
   d_b = d \cdot \cos\alpha
   $$
   ```

3. 只有在文档需要交叉引用且渲染器支持时才给公式编号；编号格式应与目标环境一致。公式符号、上下标和变量命名要保持一致。
4. 代码使用围栏代码块，并在已知语言时标注语言：

   ````markdown
   ```python
   print("hello")
   ```
   ````

5. 表格使用目标环境支持的 Markdown 表格语法。列数保持一致，表头表达字段含义；复杂布局不要靠大量空格伪造。

## 六、空白、分隔线与元数据

1. 连续空行通常最多保留一个，文末保留一个换行。
2. `---` 表示有语义的主题分隔，不当作装饰线连续堆叠。
3. 列表项保持连续；嵌套列表使用缩进，不用额外空行伪造层级。
4. YAML frontmatter 不是所有 Markdown 环境都支持。只有目标工具或项目确实需要时才添加，并只写约定好的元数据。
5. 不要为了建立“图谱边”把大量链接塞进 frontmatter；语义关系优先放在正文相应位置。目标工具若有明确的元数据字段要求，以工具约定为准。

## 七、语言与混排

1. 按文档主要语言使用一致的标点、引号、大小写和空格规则。
2. 中文与英文、数字之间是否加空格，遵循项目或出版规范；不要把这一习惯强行套到代码、公式、链接、版本号、文件名和标准号中。
3. 代码、公式、链接、文件路径和专有格式中的字符不要为了排版擅自改写。

## 八、跨来源迁移

迁移前先确认源格式、目标格式、目标编辑器和项目约定。转换时遵循以下原则：

| 源内容 | 通用处理原则 |
|---|---|
| 文档标题 | 根据目标环境决定是否保留正文标题，避免与文件名或界面标题重复 |
| 标题层级 | 保留相对层级；目标不支持的层级才做最小必要调整 |
| 表格 | 转成目标环境可解析的表格，不用空格模拟复杂布局 |
| 文档链接 | 映射到目标文档的相对路径、标题锚点或目标工具扩展 |
| 图片与附件 | 按第四节归置：进目标项目的附件目录，更新引用并检查是否存在 |
| Callout、分栏、网格 | 目标支持就保留；不支持时转换为语义清楚的线性结构 |
| 不可转换对象 | 保留必要的文字说明，并在报告中列出未完全还原的部分 |

迁移不是内容重写。源文档中的事实、顺序、公式和引用关系应尽量保持；格式不确定时先保留并报告，不要用猜测替代原内容。

## 九、写、改与检查的工作流

1. 先读取目标项目的说明、编辑器配置和已有样例，确定采用通用 Markdown 还是某种扩展语法，以及附件目录在哪。
2. 对现有文档先做只读扫描，记录标题、链接、资源和公式的现状。
3. 只做必要的局部修改，避免整篇重写导致内容、链接或格式丢失。
4. 修改后重新扫描；必要时用目标渲染器预览，检查标题层级、链接解析、图片显示、公式和代码块。
5. 回读改动区域，确认内容事实没有变化。
6. 报告结构问题、未解析链接和无法迁移的对象；不要把内容疑问伪装成格式已修复。

大范围批量重排前，先列出受影响的目录、文件类型和规则。用户未确认时，不要对整个库进行不可逆的批量重写。

## 十、校验脚本

本 skill 附带的扫描器只读检查 Markdown 结构，不默认绑定任何知识库：

```bash
python3 /path/to/law-md-write/scripts/check_md_structure.py <目标文件或目录>
```

需要把问题作为测试失败处理时使用 `--strict`。独立文档需要强制 H1 时使用 `--require-h1`；项目明确采用显式章节编号时使用 `--numbered`：

```bash
python3 /path/to/law-md-write/scripts/check_md_structure.py --strict --require-h1 <目标目录>
python3 /path/to/law-md-write/scripts/check_md_structure.py --strict --numbered <目标目录>
```

需要按 4.2 的附件集中约定检查时，显式传入附件目录名（相对库根，库根由目标路径向上查找含该目录的层级确定）：

```bash
python3 /path/to/law-md-write/scripts/check_md_structure.py --attachments-dir 附件 --strict <库根或笔记目录>
```

传入该参数后额外检查两件事：扫描范围内的媒体文件是否都落在附件目录内（`附件未集中`），以及每条附件引用能否按文件名命中（`附件引用未解析`）。

默认检查：标题跳级、代码围栏中的误判、行内 `$$`、连续空行和本机绝对路径链接。不传 `--attachments-dir` 时，脚本不会去判断某个目录是不是“附件”，也不会把某个私人知识库的目录事实写进结果；附件相关检查只按命令行显式指定的目录名执行，媒体类型也只按常见扩展名识别。

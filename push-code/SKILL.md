# Push Code：主控分派与独立聊天开发

目标是交付一批范围明确、可验证的改动，同时让主控聊天随时能规划和分派新需求。主控与用户对齐需求、冻结技术方案后，将执行闭环交给独立聊天；派发完成就结束本轮，不持续陪跑。

## 适用范围与授权

- 用户要求独立功能、新聊天或 worktree 批次开发时使用。单点 bug、文案、已明确改法的小修可在当前聊天完成，不强制拆分。
- “修改这个 skill”只授权修改 skill，不启动开发批次。
- 新聊天、向其他聊天发消息、提交、推送、部署分别遵守当前工具权限与用户授权。skill 自身不提供授权；用户已明确授权的本批动作不重复确认。
- 项目事实、安全约束、构建命令遵循仓库 AGENTS.md。不要在本 skill 再维护一套项目规范。

## 角色：聊天与 agent 不混用

- **主控聊天**：需求对齐与技术方案由主控负责。先把需求拷问清楚：目标、反例、失败场景、优先级、本批边界和可能的后续演进逐条对齐，模糊就停下讨论（见下节）；再给出技术方案——路线、关键取舍、影响面、实现成本，经用户拍板后冻结为本批契约。为实现方案所需的代码阅读和限时调研由主控完成；写完契约后负责分派、按需查看状态、决定交付与整合顺序。编码、原型验证、真机验收、review 组织和修复交开发聊天，主控不接手实现，也不以“小修”“接线”或“帮助验收”为由持续参与。
- **开发聊天**：每个独立可交付功能一个侧栏可见的新聊天、一个独立 worktree、一个分支。按已冻结的技术方案完成从实现到测试、真机验收、组织独立 review、修复和交付记录的闭环，不在每个阶段等待主控放行。实现中发现方案不可行，提出最小待决问题交回主控，不自行换方案；方案未变的前提下自行处理实现细节。共享状态或同一批文件强耦合的工作留在同一个功能内，不为了并行硬拆。
- **agent**：仅用于限时调研或只读 review，可由主控或开发聊天发起，不作为开发聊天的替代，不承包功能实现或代替开发者改代码。
- 不强制另设 acceptance agent。一次针对需求的黑盒检查由开发聊天或指定验收者执行，reviewer 和主控复用记录，不重复操作同一流程。
- 开发聊天默认使用用户惯用模型与高强度；模型按宿主实际可选值指定（Qoder 用设置接口 getModels 返回的 modelKey，显示名不能当 key），用户另有指定时服从用户。调研与 review 不自动提升到最大思考强度。

## 主控先对齐需求与技术方案

派发前主控必须完成两件事，缺一不可：

- **拷问需求**：不接受模糊表述。目标是什么、现在怎么凑合、什么情况算失败、哪些用例必须支持、哪些明确不要；一次只问少数关键问题，能给出推荐选项的就给，不逼用户在无法判断的取舍上选。目标仍模糊就停下，不定契约。
- **拓展性思考**：推演边界之外的可能演进（入口变多、数据量增长、共享状态、旧数据兼容、后续功能挂靠），判断本批要不要为它们留接口或数据形态；本批不做的记入后续项，不悄悄扩进本批范围。

范围清楚且方案已拍板就直接写入任务记录并推进，不要求用户再次批准每个实现细节。只有产品语义、存储方案、安全边界或显著成本未明确时才提问。

每个功能写清：
1. 这批结束时用户能做什么，以及明确不做什么。
2. 技术方案：采用的路线、关键取舍、影响面、已知成本；由主控给出并经用户确认。
3. 拓展性结论：本批边界外需要预留的接口或数据形态，以及记入后续项的演进方向。
4. 基线、负责人、worktree 和文件归属；不确定的路径在宿主创建后补齐。
5. 核心验收：实际入口、预期结果和主要失败场景。
6. 必须保留的数据不变量及所需检查。
7. 起始时间、截止时间、预计交付物，以及会阻止交付的问题。

普通功能用几条说明即可。同步、迁移、共享状态存在重要歧义时才补 [模型模板](references/model-first.md)；不预先穷举整个产品的入口与状态笛卡尔积。技术路线不确定时才读 [调研指引](references/open-source-research.md)。

新发现先分类：本批阻断缺陷必须修；非阻断缺陷与增强建议记录到后续项，不自动变成这一批的新需求。用户改变架构或方向时，保存旧实现，明确本批替换后的范围与剩余预算，不把两套方案一起做完。

## 会话工具与 worktree

先通过当前工具清单发现实际接口并读 schema，只使用宿主实际存在且已获授权的接口，不假设 worktree 或回调能力。常见对照：

| 用途 | Codex | Qoder Desktop |
|---|---|---|
| 发现项目/工作区 | `list_projects` | `list_workspaces` |
| 创建开发聊天 | `create_thread`（project + worktree） | `create_chat_session`（workspaceId，无 worktree） |
| 读取会话 | `read_thread` | `read_chat_session` |
| 有界等待/快照 | `wait_threads` | `wait_chat_sessions` |
| 发送纠偏 | `send_message_to_thread` | `send_message_to_chat_session` |
| 完成回调 | 宿主提供则用 | `callbackMode: "supervise"` |
| 模型指定 | 模型名 + 思考强度 | 设置接口 getModels 的 modelKey |

1. 用户已明确授权所列独立聊天与 worktree 后，先用宿主的工作区/项目发现工具找到正确目标。
2. 用宿主的会话创建工具创建侧栏可见的开发聊天。prompt 必须自包含任务契约、已冻结的技术方案、基线、边界、检查和停止条件，参见 [分派模板](references/prompts.md)。
3. worktree 按宿主能力处理：宿主能在创建时自动生成（如 Codex 的 project + worktree 目标）则开发聊天只核对实际路径、分支和 HEAD，不再建第二份；宿主不提供 worktree（如 Qoder 的 `create_chat_session`）则由开发聊天在第一步自己 `git worktree add` 一份，或由主控提前建好并把路径写进 prompt，只建一份，不覆盖已有工作树。分支默认沿用宿主或项目约定，手动创建时按宿主用 `codex/` 或 `qoder/` 前缀。
4. 创建是异步的。保留返回的会话标识（Codex 的 threadId / hostId，Qoder 的 sessionId / SessionRef）；只拿到临时 ID 时按宿主支持的查询方式等待真实标识，不把临时 ID 传给读取/等待/发送接口。
5. 确认开发聊天已启动后，记录会话标识、worktree、分支、基线、范围、截止时间与状态，向用户提供聊天入口并结束本轮。不要进入连续等待/读取循环，也不要另建循环等待任务来占住主控。创建尚在排队时如实报告排队状态，不把它写成已启动。
6. 宿主提供完成/交互回调时创建即开启（如 Qoder 的 `callbackMode: "supervise"`），回调到达再读会话；没有回调的宿主，在用户问进度、要求巡视或准备接收交付时用等待接口的 `timeoutMs: 0` 做一次有界快照，必要时再读取，无变化就返回。只有用户明确要求本轮持续盯到结束时才持续等待。用宿主的发送工具发送已获授权的本批纠偏，不改变其任务范围。
7. 开发聊天通过正常进度消息和最终答复汇报，不自行给其他聊天发送消息。默认不承诺主控回合结束后会自动轮询或自动醒来；若宿主没有明确支持该能力，就在下一次用户交互时查看结果。开发执行不依赖主控持续在线。

主控收到新需求时，直接开始新需求的讨论、边界划分与分派，不等旧批完成。独立改动从明确的稳定基线创建另一份 worktree；依赖旧批或触及相同共享文件时记录依赖与整合顺序，不能把旧批未提交修改混进新基线，也不因此接管旧批开发。产品语义、授权或外部条件确实阻断时，开发聊天保全现场并说明最小待决问题；其余已明确的实现自行推进。

缺少创建可见聊天或 worktree 的能力时，明确报告，保留只读准备结果；不能静默改用子 agent 或当前聊天代做，也不能编造已创建成功。其他独立且已授权的工作可继续。

## 验证与 review：一次取证，按风险复用

- 开发聊天先运行与改动有关的检查，并从真实入口完成核心路径。小修通常是一个复现场景加一个直接回归。
- UI 缺陷需要真实窗口证据；内部脚本、单测不能冒充鼠标操作或手感验收。已有截图、录屏、步骤和数据断言可以给 reviewer 复用。
- 多聊天共用一台电脑时，同一时刻只有一个电脑控制者；其余先做非 UI 工作。用户中断电脑控制后停止操作，未完成项如实记录。
- 同步、迁移和存储按实际风险检查：覆盖或删除前的基线校验、写失败保留输入、并发冲突、必要的重启或中断恢复。只测改动影响的类型和路径；真实服务未验证就说明，不用模拟服务结果代替。
- Review 默认一轮加一次定向复核。常规功能一个 reviewer；同步、迁移、存储等高风险功能默认两个不重叠的视角。范围与模板见 [review 指引](references/review-depth.md)。
- reviewer 只拦真实的需求缺失、缺陷、数据风险和必要验证缺口。建议重构、风格偏好、无证据的假设不自动阻断交付。
- 必需检查失败或存在数据安全问题时不得合并。完成验证后，同一代码状态不重复全套；修复后只补受影响检查，整合后按仓库要求集中跑一次完整检查。

## 收敛与停止

默认每个交付批次 **2 小时总预算**，用户可明确指定其他预算；调研、实现、review 和验证都计入其中。任务显然超过预算时，先拆成可独立验收的小批次并说明，不承诺在一个长回合完成整个子系统。使用当前时钟记录截止时间，不凭 token 数估计。

- 调研默认最多 20 分钟，给出可决策结论；不为了凑候选或全面性继续搜集。
- Review 默认最多 20 分钟，优先交出有证据的阻断项；这不是额外增加的批次预算。
- 连续约 30 分钟没有新的可运行路径、有效测试结果或已定位的阻断原因时，重新缩小问题，不继续泛化重构。
- 到达批次截止、同一阻断重试两次仍无新证据、两轮审查后仍有阻断，或缺少必需的外部条件时，结束依赖该条件的工作。
- 停止前完成必要的数据保全和原子操作，保存可恢复的代码与验证记录。是否创建检查点提交遵循现有授权。
- 汇报已完成、未完成、具体阻断、下一步最小动作。未完成就是未完成；不能为了按时通过而跳过安全检查，也不能自动延长预算、换 agent 或开启下一批继续通宵。
- 用户明确延长或选择下一批后再继续。无回复不表示延长授权。其他未受阻的已授权任务仍受原预算约束。

## 整合、交付与清理

主控按需接收真实 diff、提交与验收记录，确认交付范围和本批阻断项状态，决定整合顺序。整合的实际操作、合并冲突修复、集中检查、试用包与安装准备交原开发聊天或明确指定的整合聊天；主控不在自己的回合接管这些执行工作。执行者遵循已有授权，未获整合授权时止于可审查分支和记录。多个功能只指定一个整合执行者，同一主分支或交付目录不得并发写入。

基线前进时，执行者按项目约定更新分支并处理冲突；对改变的部分复核，不重新审查已无变化的全部功能。优先保持线性历史，不强推覆盖远端。

提交、推送或安装仅在用户授权范围内执行；已经明确要求“review 通过后推送”等，不再重复索取同一授权。部署前准备具体可审查产物；应用仍运行时不强关，先备份并请用户正常退出，再校验替换结果。

只清理本批创建、已整合且干净的 worktree 与分支；先核对路径、归属、合并状态和未提交修改。不强删、不清理其他任务的工作。其他尚在开发的 worktree 不阻止已完成主分支的正常推送。聊天由用户管理，未经授权不自动归档或删除。

最终答复说明交付结果、实际验证、剩余限制和产物位置；将“源码完成”“已提交”“已推送”“已安装”分开说明。

# push-code

## Overview

多功能开发批次使用这个流程。主会话是主控：对齐方向、拆分、委派、强制 review、整合、验证、交付和清理。主会话不亲自实现功能代码，除非用户明确要求做一个小修。

**只在用户明确调用时启用**：普通开发或普通代码修改不要自动套用这套流程。

**项目事实以仓库 AGENTS.md 为准。** 本 skill 只写开发节奏、批次编排、review 和验收流程；代码架构、数据安全、产品原则、构建命令不在本 skill 重复。仓库要求与本 skill 冲突时，先指出并让用户拍板，不要两边各做一套。

**决策必须先拍板**：交互手势、产品行为、存储方案、Skill 的设计与内容，都必须先把选项、取舍和影响摆给用户，得到明确批准后再实施。不要把“可以”“做”“推进”当成对未列出细节的授权；先做后问视为错误。

## 角色

- **主控（当前会话）**：方向讨论、任务拆分、文件归属、审阅方案与真实改动、合并、集中验证、交付、清理。
- **执行会话**：一个独立功能一个会话、一个 worktree、一个分支；负责开发、定向测试、本地提交（不 push、不合并 main）。
- **review agent**：每个 worktree 完成后，在执行会话内启动的**新 agent**，只读审查，不能由开发会话自审。
- **acceptance agent**：黑盒验收者，只按用户场景、原型/契约和模型操作真实窗口/CLI，不先读实现；不能由开发会话自验收。

具体开发会话和执行 agent 默认使用 Terra（gpt-6.1-terra），思考强度 high（高）；Fullstop 另有指定时按指定执行。

## 1. 对齐方向

- 先读仓库 AGENTS.md 指定的文档（README、ARCHITECTURE、CONTEXT），确认当前计划、排队顺序与数据/构建约束。
- 先讨论再动手：产品取舍、交互方式、数据安全等问题用 AskUserQuestion 让用户拍板；未确认时只做只读探查。
- 交互细节（普通点击/修饰键/右键菜单）、存储方案和 Skill 结构要先列出选项与取舍，等用户逐项确认；简短回复只覆盖已经列出的内容，不覆盖未列出的细节。
- 新需求默认接在已批准计划之后，不打断正在执行的任务；不为安排新功能而重排当前批次。
- 主动对照参考软件、现有实现和真实操作流程，发现并指出缺口，提出改进并推进授权范围内的开发；不要把已发现的问题只留在报告里。
- 主动性不等于擅自扩大范围：新增重要产品方向、改变用户数据、引入明显维护成本前，说明具体方案与取舍；已获准范围内持续推进，不为每个实现细节重复确认。

## 2. 模型门槛（新功能 / 跨模块）

补丁多的常见原因不是代码不会写，而是把功能当界面做：入口没盘全、状态组合没枚举、隐式状态没有唯一来源。按规模分档：

- **完整门槛**（新功能、跨模块、改标签/会话/存储/共享状态、新增用户可感知规则）：先写一页模型，用户明确拍板后再建 worktree。
  - 入口清单：用户能到达该功能的全部路径——点击、修饰键、中键、右键、快捷键、拖拽、重启恢复、外部打开。
  - 状态矩阵：行 = 入口，列 = 当前状态（如文档/画板/文件夹/草稿/功能页/锁定）× 修饰键 × 是否跨重启；每格写预期结果。
  - 不变量：例如“有活动文档就一定有对应标签”“任何替换前先保存”“会话快照从同一模型派生”。能放进类型或断言就不只写注释。
  - 单一命令：状态型 UI 只保留一个打开/切换命令（replace / new / beside 等模式），所有入口复用，不各写一套。
  - 异常态：空、加载、保存失败、外部修改、权限/同步盘只读、缺失文件。
  - 开源调研（大功能/不熟悉领域）：自主先做，不等用户提醒。找 2–4 个活跃的开源实现（本地参考仓库、GitHub、官方文档），比较数据模型、交互、持久化、撤销、协作和许可证；技术栈不同就提炼业务逻辑与状态模型，不硬搬代码。输出候选对比表、推荐、可借鉴/避免清单、许可证与依赖风险、来源链接和日期。新增依赖或复用代码先拍板。
  - 决策留痕：批准的语义写进 docs/CONTEXT.md 或任务记录；简短回复只覆盖已列出的项，未列出的必须再问。
- **轻量门槛**（单点 bug、文案/样式、改法已明确的修复）：至少列出“受影响入口 + 回归路径 + 其他调用方”，不强制整页矩阵。

完整门槛（含大功能调研简报）未获批准不建开发会话。模板见 [模型与不变量模板](references/model-first.md) 和 [开源调研模板](references/open-source-research.md)。

## 3. 拆分与并行

- 只并行真正独立的功能；为每个 worktree 明确文件归属，避免两个会话同时改同一批文件。
- 按状态所有权拆分，不只按界面：同一状态模型/共享文件不拆给两个并行会话；在 prompt 里写明各自负责的矩阵行与不变量。
- 批次保持小而完整；先做低风险小修，再做需要方案的大功能。
- 为每个任务确定 worktree 路径、分支名（如 `qoder/<slug>`）和基线 main HEAD。
- 拆分方案（做哪些功能、每个会话的文件归属、哪些并行/串行）先给用户确认，再创建会话。
- 大功能第一轮只做模型 + 开源调研简报（入口、矩阵、不变量、候选对比、推荐、风险），用户批准后再实现；调研由执行会话自主完成，不等用户提醒。
- 并行开发只在批次内成立；普通单会话开发不需要 worktree，也不套用本流程。

## 4. 委派

- 用内置 `create_chat_session`（默认 agent，`callbackMode: supervise`）创建独立会话。新会话没有历史，prompt 必须自包含：仓库路径、基线 HEAD、需求、边界、验证方式、汇报格式。
- prompt 还要带模型：完整门槛附入口清单、状态矩阵、不变量；轻量门槛至少写受影响入口与回归路径。要求先核对模型再写代码，状态型功能只通过单一命令。
- 大功能还要要求先做开源调研简报（2–4 个候选、近期活跃度、许可证、可借鉴的业务逻辑/避免项、来源链接和日期）；不要凭印象推荐库或方案。
- 委派时说明本批 review 档位（L1/L2/L3）与预计团队数，让执行会话知道完成后要按什么深度启动 review。
- 要求补接线测试或真机场景，不能只交纯函数单测；汇报里给出矩阵覆盖与未验证组合。
- 要求执行会话自己建 worktree：

```sh
git worktree add -b qoder/<slug> "<worktrees-root>/<slug>/<repo>" main
```

- 统一约束：不 push、不合并 main、不跑仓库禁止的格式化（如 rustfmt）、不启动或强关用户正在用的预览窗口；遵守仓库 AGENTS 的代码、数据和构建约束。
- 大功能或方向不完全确定时，第一轮只做只读调研并交方案；**用户批准后**再动代码。

## 5. 跟踪

- 优先依赖 supervise 回调，不要轮询；需要看进度时用 `read_chat_session`，需要纠偏时用 `send_message_to_chat_session`。
- 「Turn 完成」不等于工作被接受：读最终汇报并用 `git log` / `git status` 核对实际状态。
- 会话执行失败时先读现场，工作通常已保留；让原会话从断点继续，不要另起重复实现。

## 6. 完成定义与场景验收（通用开发节奏）

代码 review 只证明 diff 层面；功能完成必须同时满足下面几条，任何一条没做都要在汇报里列为未验证，不能用测试数量代替用户可用结果。

- **真实入口**：从用户实际使用路径走通——侧栏、主页、搜索、文档内引用、画板卡、外部打开、重启恢复。不能用内部脚本命令（如 `pdf-open`、直接调用 Workspace 方法）代替用户入口。
- **原型对照**：UI 改动对照已通过的原型，逐项核对位置、尺寸、出现/隐藏时机、空态、错误态、减少动态；没有原型时对照现有实现或参考软件。原型只作视觉标准，不把原型样式整段搬进工程。
- **异常态**：空、加载、保存失败、外部修改、权限/同步盘只读、缺失目标、冲突副本；逐项确认用户看到什么、数据是否保留。
- **重启恢复**：标签、页码、滚动位置、草稿、锁定状态、当前功能页；跨重启不丢用户状态。
- **长时间/后台**：有定时器、周期刷新、文件监视、同步盘、自动保存的功能，连续使用 10–15 分钟，并模拟文件瞬时移走、只读、冲突副本；不能只打开几秒截图就算通过。
- **未验证清单**：汇报写清哪些入口、状态、平台、组合没验；无法实测时明确说明，不把编译/单测通过写成功能可用。
- **用户反馈优先**：用户报告的手感、布局、跳转、丢失问题按 P1 验收缺口处理，先归类（规则变更/未枚举组合/隐式状态/验证缺口），补矩阵和 E2E，不能只修当前症状或降为样式微调。
- **主控亲自走**：合并和交付前，主控亲自从真实入口走黄金路径 + 至少一个异常态；只看 diff、汇报或截图不算验收。

### 场景清单按改动范围定

不维护固定场景库，也不按功能类型抄模板。每次根据本次开发内容，从模型的入口清单 × 状态矩阵推导：

- **小修**（单点 bug、文案/样式、改法明确）：1–2 条，只覆盖改动的入口/状态 + 一个直接回归；不要求跑完整功能套件。
- **常规功能**：覆盖新增/改变的入口和状态，至少黄金路径 + 一个异常态。
- **新功能/跨模块/高风险**：入口 × 状态矩阵全量，加数据断言、异常、重启、soak/同步盘。
- 用户报过的 bug：在任务记录里留一条最小回归场景；下次碰同一区域时重跑，不建常驻目录。
- 场景写在委派 prompt / 任务记录里；开发会话先写草案，acceptance agent 独立再写一份，两份对比找缺口。

每条场景写清：用户目标、入口、真实手势、预期可见结果、数据断言、异常/重启、证据。

### 独立验收

- 开发会话不能验收自己的功能；每个功能由**新的 acceptance agent** 黑盒验收。
- acceptance agent 只看用户可见变更、原型/契约和模型，不先读实现；可加对抗场景。
- 多 worktree 批次做 A/B 互验：A 的功能由 B 验，B 的功能由 A 验；单功能批次用独立 acceptance agent。
- 验收必须用真实手势；`pdf-annotate`、直接调 Workspace 方法、脚本截图只能做前置或 soak，不能作为手势证据。
- 证据：关键状态按顺序截图 PNG + 数据断言（文件/sidecar/JSON）+ “我实际运行/查看了什么”。
- P1 场景失败阻断合并；小修只跑改动场景，但失败修复后要重跑该场景组。

## 7. Review（强制，按复杂度分档）

- 每个 worktree 完成后、合并前，向该会话发 follow-up：按复杂度启动 **1–4 个独立 review agent**，只读审查 `git diff main...HEAD`。主控在发 review 前定档，并在 follow-up 里写明档位、团队数和各自范围；模板见 [review 分档](references/review-depth.md)。
- **L1 轻量**（单点 bug、文案/样式、改法明确）：1 个 reviewer，聚焦 diff、回归、真实缺陷和测试缺口；不为小修堆流程。
- **L2 标准**（常规功能、跨文件、UI 行为、状态型改动）：1–2 个 reviewer；至少一个查需求/模型/接线，必要时再加数据/测试。
- **L3 深度**（新子系统、存储/编辑内核/会话/同步、并发/迁移/数据安全、大功能、新依赖/许可证风险）：2–4 个 reviewer，范围不重叠，按需拆成正确性与不变量、UI/交互与真机证据、测试/失败模式、依赖/许可证/架构；不能把新子系统压给一个 reviewer。
- **严格模式**：如果会话工具或 MCP 不可用，暂停 review 和合并，等连接恢复后继续；不要用主控本地 review agent 替代会话内审查，也不要跳过 review 直接合并。
- 审查重点：需求符合度、真实缺陷与遗漏、数据安全、测试缺口；不做风格挑刺。结论按严重程度列出并带文件:行。
- 同时审查模型覆盖：入口是否盘全、状态组合是否漏、隐式状态/单一来源是否被破坏、是否只有纯函数测试而没有接线或真机验证。
- 大功能同时看调研简报：候选是否近期活跃、许可证和依赖风险是否说明、借鉴的是业务逻辑还是代码、来源是否可验证；不要接受“看起来像”的结论。
- **UI/交互类 review 必须看真实窗口**：reviewer 要实际运行或查看主控提供的真实窗口截图/录屏，并对照已通过的原型；只读 diff 不能关闭 UI 验收项。reviewer 汇报必须写明“我实际运行/查看了什么”，没跑 UI 不能给 UI 通过。
- 每个 reviewer 必须列出未覆盖的组合和建议补的 E2E，不能只给通过/不通过；L3 必须所有范围返回，任一 P1 阻断合并；L2 至少一个 reviewer 给出未覆盖清单；L1 只拦真实缺陷。
- 开发会话汇总去重多个 reviewer 的结论，不把重复项当新发现；确认成立的问题**新增 commit**（不 amend、不 push），重跑受影响测试后再汇报。review 不通过不合并。
- 修复必须说明根因分类（规则变更/未枚举组合/隐式状态/验证缺口），并带对应测试或文档更新，不能只打补丁。
- **review 与 acceptance 是两道门**：review 通过不等于功能验收；UI reviewer 看真实窗口和原型，但不能替代独立 acceptance agent。完成定义与场景验收见第 6 节。
- 已合并的分支也补 review；有修复再合并一次。

## 8. 补丁分类（发现回归时）

先定性再改代码，避免用补丁掩盖模型问题：

1. **规则变更**：产品语义变了 → 更新决策记录和矩阵，再改实现；不要继续修旧规则。
2. **未枚举组合**：补矩阵行/列和接线测试，不只修当前入口。
3. **隐式状态/架构耦合**：收敛到单一来源/单一命令，修一类而不是一处。
4. **验证缺口**：补真机 E2E 或脚本场景，不能只补单测。

修复 commit 要说明属于哪类、补了什么测试/文档；review 先看是否只修了表面。用户报告的手感/布局问题优先归为“未枚举组合”或“验证缺口”，按 P1 处理。

## 9. 整合与交付

- 主控亲自看 diff（`git show`），不能只看汇报。
- 合并前必须有 acceptance agent 的场景验收报告；P1 未通过不合并。主控再亲自走黄金路径 + 一个异常态。
- main 前进后先 rebase 分支，再 `git merge --ff-only`；保持线性历史。
- 每个整合后的代码状态集中跑一次仓库完整检查（有 `scripts/check.sh` 就跑它）；同一状态通过的结果直接复用，只对受影响部分补测。
- 按约定构建和交付；用户窗口在运行时不要强制关闭，先准备新二进制或请用户关闭后重启。
- 试用版本由主控统一整合和交付，记录来源及包含的功能；验收哪份构建，就交付哪份。用户明确要求单独运行某个分支时照办并说明范围。
- 合并和清理可以按流程做；**push 前必须单独询问用户**，得到明确同意后再推送。归档会话同样先问，不要擅自批量归档。
- 推送前先完成第 10 节清理：主工作区干净、只剩主 worktree、已合并的 `qoder/*` 分支已删除；还有未合并/正在开发的 worktree 时暂缓推送并汇报。

## 10. 清理

推送 GitHub 前必须完成清理：仓库只保留主工作区和 main 分支（用户明确要求保留的除外）。

- 每批合并后执行 `git worktree list` 和 `git branch --merged main`。
- 只删除「已并入 main 且 worktree 干净」的分支：

```sh
git worktree remove "<worktree-path>" && git branch -d "qoder/<slug>"
```

- 推送前依次确认：`git status --porcelain` 为空、`git worktree list` 只剩主工作区、`git branch --merged main` 没有遗留已合并的 `qoder/*` 分支。
- 未合并/正在开发的 worktree 保留，但不在该状态下推送；先把保留清单汇总给用户。
- 只从主工作区推送 main；推送前单独询问用户。
- 保留正在开发的 worktree；其他工具遗留的 detached worktree 未经用户确认不要删。
- 在汇报里列出保留和删除的 worktree；归档已完成会话前先问用户，不要擅自批量归档。

## 11. 文档一致性

行为、规则、存储、UI 或构建方式改变后，同步更新描述它的文档；同一规则只留一个来源。

- 项目事实、架构、代码约定、数据安全、构建命令：仓库 `AGENTS.md`；`CLAUDE.md` 与其保持逐字节同步。
- 开发节奏、模型门槛、review 分档、完成定义、交付与清理：本 skill。
- 构建/测试/打包步骤：`CONTRIBUTING.md`。
- 动效原则、参数、减少动态：`docs/MOTION.md`。
- 存储格式：`docs/FORMAT.md` / `docs/ARCHITECTURE.md`；当前状态与排队：`docs/CONTEXT.md`。
- 功能盘点与验收边界：`docs/BOARD_STATUS.md`。
- 改了行为或规则，先找现有文档里的对应段落，再改代码；不要新增第三份规则。规则搬家时在原处留一句指针。
- 合并/交付前检查 README、CONTRIBUTING、ARCHITECTURE、FORMAT、MOTION、BOARD_STATUS、CONTEXT 是否有与新行为冲突的表述；有冲突先修正再交付。
- 用户报告的 bug 在任务记录或 `docs/CONTEXT.md` 里留一条最小回归场景；下次碰同一区域时重跑。不建常驻场景库。

## 测试门槛

- 核心/存储/编辑内核改动：跑定向测试，按仓库要求补 fuzz 种子；交付前跑完整检查。
- UI 改动：优先使用平台自带的电脑控制（computer-use skill / 宿主提供的 Node REPL 与 Computer Use SDK）实际运行、操作软件并查看真实窗口行为；截图保存成文件并给出绝对路径。编译和单测不能代替体验验收；无法实测时明确说明。
- 状态型 UI 改动：除定向单测外，跑真机 E2E 黄金路径和边界（打开/锁定/重启恢复/文件夹导航/引用跳转等）；能脚本化就加场景。纯函数测试通过不代表入口接线正确。
- 长驻/同步类改动：按第 6 节做 soak 和文件瞬时缺失/只读/冲突副本模拟。
- 测试库按仓库 AGENTS 的规则：自动化/脚本/回放用隔离临时库；人工试用用指定试用库或其副本；绝不碰用户真实库。
- 无法实测时明确列出未验证组合，不以测试数量代替体验结论。
- 一个代码状态只跑一次完整检查，不要为每个小提交重复全套。

## 汇报

- 先结论和影响，再给细节；说明实际做完、尚未完成和验证边界。
- 状态型功能报告矩阵覆盖：已验证哪些入口/状态、哪些没验；给出用户可复测的路径。
- 大功能先汇报开源调研结论：候选、推荐/不推荐理由、可借鉴的业务逻辑、许可证与依赖风险；再谈实现。
- 规则变更与 bug 修复分开说明，不要把语义变化混成“修复”。
- 告诉用户可以实际测试什么；不要用提交数、测试数量或流程执行次数代替用户可用的结果。

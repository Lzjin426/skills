# 开源调研模板（大功能 / 不熟悉领域）

用于 push-code 完整门槛。大功能开工前由执行会话自主完成，不等用户提醒；小修不做整页调研。

## 1. 何时做

- 新功能或大改版（画板、日历、关系图、编辑器核心等）。
- 方向不唯一，存在多种成熟实现或交互范式。
- 技术栈不熟，或不确定该自研、借鉴还是引入依赖。
- 用户明显在用同类产品（Obsidian、AFFiNE、tldraw、Excalidraw 等）。

## 2. 先本地，后网络

1. 仓库内已有的参考源码、`docs/research/` 报告、复制的上游分支。
2. GitHub 搜索 / trending / releases / issues；用 `gh` 查 stars、最近提交、release 日期。
3. 官方文档、设计说明、数据格式文档、迁移/导出说明。
4. 包管理器/依赖生态（能否在 Rust/GPUI 里用，还是只能借鉴）。

时间盒：大功能 30–60 分钟，候选 2–4 个；不要变成无限调研。网络不可用时明确说明。

## 3. 候选对比表

| 候选 | 近期活跃度 | 许可证 | 平台/技术栈 | 功能覆盖 | 数据模型 | 交互/UX | 持久化/撤销/协作 | 维护风险 | 适配度 |
|---|---|---|---|---|---|---|---|---|---|
|  | 最近提交 / release |  |  |  |  |  |  |  |  |

“近期热门”不能只看 stars：同时看最近提交、release 节奏、issue/PR 活跃度和近一年是否维护。

## 4. 技术栈不一致时提取什么

- 领域模型：节点、边、分组、引用、嵌入、注释、版本。
- 命令模型：移动、缩放、框选、对齐、吸附、层级、组合、撤销/重做。
- 数据格式：文件结构、ID 稳定性、外部引用、迁移和导出。
- 状态机：空/加载/错误/只读/协作冲突/离线。
- 交互范式：手势、修饰键、右键菜单、键盘、触控板。
- 性能与边界：大画布、海量节点、缩略图、增量渲染。
- 失败案例：issues 里反复出现的问题，往往比 README 更有用。

技术栈不同就提炼业务逻辑与状态模型，不硬搬代码；把概念映射到本项目的 Rust/GPUI 和 Markdown 真源。

## 5. 许可证与依赖

- 先看 LICENSE：MIT/Apache/BSD 与 GPL/AGPL/SSPL、自定义许可证区别很大。
- 借鉴思路/交互/业务逻辑通常没问题；复制代码、内嵌资源、加依赖前必须确认许可证并记录出处。
- 不把“看起来能用”的库直接加进依赖；新增依赖要说明体积、维护、跨平台和替代方案。
- 记录候选的许可证、版本、来源链接和查看日期，避免以后无法追溯。

## 6. 输出简报（给用户拍板）

```text
调研结论（<功能>，<日期>）：
- 候选：<2–4 个，含链接、stars/活跃度、许可证、技术栈>
- 对比：<数据模型 / 交互 / 持久化 / 撤销 / 协作 / 性能>
- 推荐：<自研 / 借鉴 / 引入依赖>，理由与代价
- 可借鉴：<业务逻辑、状态模型、交互模式、边界处理>
- 不借鉴：<复杂度、许可证、技术栈不匹配、维护风险>
- 风险与未确认：<需要用户拍板的点>
- 来源：<链接 + 查看日期；离线时说明>
```

## 7. 反模式

- 只看 stars，不看最近维护和 release。
- 拿一个旧仓库当唯一依据。
- 忽略许可证，直接复制代码或资源。
- 为了“像竞品”引入重依赖，破坏低内存/低存储目标。
- 调研完不给结论、不给取舍，只堆链接。
- 把调研当实现，迟迟不交简报。

## 8. 与本项目的关系

本项目优先 Markdown 真源、Rust + GPUI、低内存低存储。调研的产出是“业务逻辑和状态模型”，不是把 Web 技术栈搬进来；新增依赖或大缓存必须主动说明取舍。

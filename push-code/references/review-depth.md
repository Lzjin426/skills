# Review 分档与团队

Review 的团队数和深度按开发复杂度定，不按 diff 行数机械定。主控在发 review follow-up 前定档，并把档位、团队数、各自范围写清楚；开发会话在同一窗口启动这些独立 reviewer，汇总去重后修复。

## 1. 定档清单

先问这几个问题，命中越多档位越高：

- 是否新增子系统、持久化格式、同步/并发/迁移、数据安全风险？
- 是否跨模块改共享状态、入口超过 2 个、或改标签/会话/编辑器内核？
- 是否有用户可感知的新交互、动效、真机路径？
- 是否引入新依赖、原生库、许可证/体积/内存取舍？
- 出错是否会丢数据、覆盖文件、阻塞启动或让用户永久看不到内容？

## 2. 档位表

| 档位 | 适用 | reviewer 数 | 覆盖范围 | 合并门槛 |
|---|---|---|---|---|
| L1 轻量 | 单点 bug、文案/样式、改法明确的修复 | 1 | diff、回归、真实缺陷、测试缺口 | 无 P1；真实缺陷修完即可 |
| L2 标准 | 常规功能、跨文件、UI 行为、状态型改动 | 1–2 | 需求/模型/接线 + 数据或测试 | 无 P1；至少一个 reviewer 给出未覆盖组合 |
| L3 深度 | 新子系统、存储/编辑内核/会话/同步、并发/迁移/数据安全、大功能、新依赖/许可证风险 | 2–4 | 正确性与不变量、UI/交互与真机证据、测试/失败模式、依赖/许可证/架构（按需） | 所有范围返回；任一 P1 阻断；P2 有明确处理决定 |

不为 L1 堆流程，也不把 L3 压给一个 reviewer。一个批次里有多个独立 worktree 时，每个 worktree 单独定档，不跨功能合并 reviewer。

### 2.1 UI/交互类 reviewer 的硬要求

- 必须实际运行或查看主控提供的真实窗口截图/录屏，并对照已通过的原型；只读 diff 不能关闭 UI 验收项。
- 汇报写明“我实际运行/查看了什么”；没跑 UI 不能给 UI 通过。
- review 通过不等于功能验收；合并前仍要按 SKILL.md 第 6 节做真实入口、原型对照、异常/重启和 soak。

## 3. L3 的范围拆分

按需选 2–4 个，范围不重叠：

1. **正确性与不变量**：状态模型、入口组合、边界、并发、迁移、数据安全、失败回滚。
2. **UI/交互与真机证据**：用户路径、修饰键/中键/右键、动效与减少动态、布局、可用性；核对主控提供的真实窗口截图/录屏。
3. **测试与失败模式**：接线测试是否真的覆盖入口、纯函数测试缺口、跨平台、权限/同步盘只读、损坏输入、性能。
4. **依赖/许可证/架构**（大功能/新库才加）：许可证兼容、体积/内存、维护活跃度、技术栈适配、是否该自研/借鉴/引入。

每个 reviewer 只回答自己的范围；不要求每个人都把整个 diff 审一遍。

## 4. 团队规则

- review agent 只读，不改代码；修复由开发会话做，新增 commit。
- 多个 reviewer 的结论由开发会话汇总去重；重复项不算新发现。
- L3 必须所有范围都返回后才进入合并判断；某个范围没跑完不能算通过。
- L1 只拦真实缺陷，不做风格挑刺；L2/L3 也按严重程度，不做无边界的美学争论。
- reviewer 必须列“未覆盖的组合”和建议补的 E2E/测试。
- reviewer 必须写明“我实际运行/查看了什么”；没跑 UI 不能给 UI 通过。
- review 通过不等于功能验收；合并前仍要按 SKILL.md 第 6 节做真实入口、原型对照、异常/重启和 soak。
- 团队规模按风险，不按提交数；超过 4 个通常说明拆分不清，先重划范围。
- 时间盒：L1 快速一轮；L2/L3 并行跑，主控不无故等待非阻塞 review。

## 5. Prompt 模板

```text
主控按 push-code review 分档：本批 <L1/L2/L3>，启动 <N> 个独立 review agent（并行），只读审查 git diff main...HEAD，不互相替代：
1. <scope A>：<具体检查点>
2. <scope B>：<具体检查点>
...
每个 reviewer 输出：P1/P2 + 文件:行 + 未覆盖组合 + 建议补的测试/E2E + 实际运行/查看了什么；不改代码。UI/交互范围必须看真实窗口或主控提供的截图/录屏并对照原型，只读 diff 不能给 UI 通过。
开发会话汇总去重，确认成立的 P1/P2 修复并新增 commit（不 amend、不 push），重跑受影响测试后再汇报。
```

## 6. 示例

- 修一个文案/按钮错位：L1，1 个 reviewer。
- 改标签打开规则/文件夹替换：L2，2 个 reviewer（需求/模型 + 接线/回归）。
- PDF 阅读器/标注、画板新子系统、store 锁/会话持久化/多机同步：L3，2–4 个 reviewer，按数据安全、交互、测试、许可证拆分。
- 已合并后才发现的问题：按问题影响重新定档，不因为“已经合并”就降成 L1。

## 备注

团队数不是质量本身；没有明确范围的多个 reviewer 只会重复。先定档、再分范围、最后汇总，才算完成 review。

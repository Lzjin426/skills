# 按风险审查与复核

只在准备 review 时读取。审查的任务是发现本批真实问题，不重新定义产品或无限补全边界。

## 选择审查范围

| 改动 | 默认安排 | 必需证据 |
|---|---|---|
| 单点修复、文案、已明确改法的小改 | 一次聚焦检查；必要时一个 reviewer | 复现场景与直接回归 |
| 独立常规功能 | 一个独立 reviewer | 核心入口、相关检查、主要失败场景 |
| 同步、迁移、存储、重要并发与数据安全 | 两个不重叠的 reviewer | 正确性与数据保护、必要失败恢复及检查结果 |

不按文件数、提交数机械增加 reviewer。原代码其他区域的问题要说明关联；与本批无关的改进不自动进入本批。

默认 reviewer 可分别检查：
- 需求接线、状态一致性及回归。
- 高风险任务中的写入基线、冲突、失败保留、恢复或迁移。

不强制额外创建 acceptance agent。核心黑盒场景由一个明确负责人执行即可，审查者复用其操作记录、截图或数据断言。多个聊天不要同时控制同一桌面。

## 阻断与建议

阻断项需要明确证据：本批核心需求缺失、可复现缺陷、可能覆盖或丢失数据、必须检查失败或缺少关键验证。给出触发条件、位置与影响。

风格、可选重构、未来规模下的假设和非阻断边角问题记录为建议，不要求开发者全部实现。未验证不等于已证实有缺陷，也不等于可以宣称通过；按实际风险决定是否阻断。

UI 审查只对真正操作过或看过的证据给结论。编译和单测不替代真实窗口；同一组证据无需开发者、reviewer、验收者和主控各重做一遍。

## 轮次与停止

一轮集中 review 后去重，开发聊天修复已确认的阻断项，再定向复核变化部分。通常到此结束，不因出现新建议重启全量审查。

默认审查最多 20 分钟，计入本批总预算。两轮之后仍有阻断或已到批次截止时，保全数据和代码，返回阻断、已有结果与最小下一步；不能跳过安全问题合并，也不能自动换 reviewer 无限重试。

所有必要检查与本批阻断关闭后即可整合，不以消除“所有可能问题”为完成条件。具体运行过和未运行过的内容都要写清。

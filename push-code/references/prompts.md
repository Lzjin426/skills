# 分派模板

仅在确需创建开发聊天或发送已授权的批次任务时读取。模板提供必要信息，不要求逐项制造审批。

## 创建独立开发聊天

先用宿主的工作区发现工具的真实返回值选择目标，再核对会话创建工具的 schema。Codex（`list_projects` + `create_thread`）示例：

```json
{
  "title": "实现选定的独立功能",
  "target": {
    "type": "project",
    "projectId": "工具返回的项目 ID",
    "environment": {
      "type": "worktree",
      "startingState": {
        "type": "branch",
        "branchName": "main",
        "onMissing": "error"
      }
    }
  },
  "prompt": "下面的自包含任务契约",
  "model": "宿主可选的模型名",
  "thinking": "high"
}
```

分支名、模型和目标以项目及用户实际要求为准。startingState 选择基线，不是指令你切换或覆盖用户当前分支。Codex 宿主自动创建 worktree，开发者不要再手动创建第二份。

Qoder Desktop 等价（`list_workspaces` + `create_chat_session`）。该宿主不创建 worktree，prompt 里必须要求开发聊天第一步自建：

```json
{
  "workspaceId": "list_workspaces 返回的 workspaceId",
  "prompt": "下面的自包含任务契约，含 worktree 创建、分支与路径要求",
  "callbackMode": "supervise"
}
```

model 需用设置接口 getModels 返回的 modelKey，不确定就省略以继承当前会话模型；agentId 按用户惯用 Agent，默认省略。宿主不提供 worktree 时，`create_chat_session` 返回的 sessionId 只代表已派发，不代表已在正确工作树里执行。

开发 prompt 示例：

> 在独立开发聊天中实现本批功能。仓库与基线：给出真实路径、分支和 SHA。宿主不自动创建 worktree 时，第一步自行 `git worktree add` 一份并核对路径、分支及 HEAD；宿主已创建时只核对，不建第二份。
>
> 本批用户结果：写出一项独立可交付结果。
> 不做：列出本批明确排除的扩展。
> 技术方案：主控已给出路线、关键取舍和影响面，按方案实现；实现中发现方案不可行，提出最小待决问题返回，不自行换方案。
> 文件归属：列出允许修改与需要协调的共享文件。
> 验收：写出核心真实入口、预期结果、主要失败场景与数据不变量。
> 检查：引用仓库要求及本次必要的测试，不复制整套产品测试表。
> 截止：写出明确时间；调研、实现和验证均在此预算内。出现阻断按 SKILL.md 的停止条件保存现场、汇报，不自动扩范围。
> 授权：明确本地提交、整合、推送、安装各自是否已获准。不修改用户真实数据、不强关用户窗口。
>
> 遵循仓库 AGENTS.md。开发在这份 worktree 内进行；不要另开实现 agent。需要调研或 review 时用限时、范围明确的 agent。
> 你是本批完整执行负责人：自行完成必要调研、参照观察、原型、编码、测试、真机验收、组织独立 review、修复与定向复核。明确模型和思考强度时原样遵守。不要把这些执行环节留给主控，不在阶段间等待主控放行；只在范围、产品语义、权限或外部条件确实阻断时提出最小待决问题。
> 主控会全程跟进本批：处理你交回的待决问题、组织独立 review、复核验收证据、决定整合顺序并盯到清理完成。你用普通进度消息和最终答复汇报，不直接给主控或其他聊天发送消息。
> 整合、集中检查、打包与安装是否由你执行，以本批明确授权为准；未获授权时交出可审查分支和记录。
> 汇报实际路径、分支、改动、验证、未验证项、阻断及下一步。存在提交时提供 SHA；未获提交授权则保留可审查 diff。

创建后确认真实会话标识（Codex 的 threadId / hostId，Qoder 的 sessionId / SessionRef）与 worktree，不以“工具已调用”当作任务已启动。只返回临时 ID 时按宿主能力有界确认，仍未就绪就记录排队状态。保存任务标识和契约，提供聊天入口，然后进入陪跑，直到审查、验收、整合与清理都有结论。

## 跟踪与纠偏

主控默认持续跟进本批：宿主提供完成/交互回调（如 Qoder 的 `callbackMode: "supervise"`）就依赖回调，到达即处理；否则用等待接口（`wait_threads` / `wait_chat_sessions`）按阶段跟进，单次等待不超过宿主上限。处理开发聊天交回的问题、组织审查和验收，不把已派发的工作丢下。新需求可立即规划与分派，新旧批次并行跟进。需要发送纠偏时，只向用户已授权协调的聊天用宿主的发送工具（`send_message_to_thread` / `send_message_to_chat_session`）发送：

> 保持原交付范围和截止时间。本次只处理已确认的阻断问题：说明证据、预期结果与受影响检查。其余建议记录后续，不顺带重构。完成后给出实际 diff、检查结果和剩余限制。

正常跟踪不更换模型，不重复创建替代聊天。工具不可用时保存任务标识并报告，不虚构回调。

## 整合执行

需要整合时，向原开发聊天或指定整合聊天提供：候选分支与 SHA、目标基线、依赖与整合顺序、已有 review 和验收证据、整合后的必要检查，以及提交、推送、打包、安装和清理的授权边界。由该聊天处理冲突、补测和产物准备；同一目标只保留一个写入者。主控盯到合并、集中检查和清理完成，复核关键证据后再结束本批。

## Review prompt

> 只读审查指定基线到候选版本的 diff。用户需求、范围、不变量、验证证据和未验证项如下。
> 你的范围仅为：明确一种风险或检查对象。时限为明确截止时间，超过后先返回已有结论与未覆盖项。
> 找实际缺陷与必要验证缺口，给文件位置、触发条件和影响；区分阻断项与建议。不要改代码、控制用户鼠标、扩展需求或派生新的 reviewer。
> UI 结论需依据真实证据；没有操作或查看证据就不声明 UI 通过。主控提供的同一份证据可以复用。
> 最终写明实际读过、执行过、未验证的内容；没有确认缺陷也明确说明。

修复后只把受影响部分与新增证据交同一 reviewer 定向复核，不默认重启全套审查。

# push-code prompt 模板

把 `<>` 占位符替换成实际内容。所有委派 prompt 都必须自包含：新会话没有历史。

## 1. Worktree 准备

执行会话在自己的第一轮里运行（路径按仓库和 slug 替换）：

```sh
git worktree add -b qoder/<slug> "<worktrees-root>/<slug>/<repo>" main
```

约定：

- 分支名 `qoder/<slug>`，基线是当时 main 的 HEAD。
- 之后所有工作在 worktree 内进行；不改主工作区。
- 不 push、不合并 main；完成后本地提交并汇报。

## 2. 委派 prompt 模板

```text
你在 Qoder Desktop 的独立会话中工作，作为执行 agent。主控会 review 并整合你的分支。
仓库：<repo-path>（<platform>，Git，main 分支，HEAD <baseline-sha>）。

任务：<one-feature-summary>

要求：
1. <requirement 1>
2. <requirement 2>
3. 文件归属：只改 <files>；不要碰 <excluded-files>。
4. 遵守仓库 AGENTS.md：不跑 <forbidden-formatter>，紧凑风格照周围代码；不改存储格式和用户数据。
5. 测试：<targeted-tests>；改了核心/编辑内核时按仓库要求补 fuzz 种子。
6. 模型：<入口清单/状态矩阵/不变量，或引用任务记录>；先核对模型再写代码，状态型 UI 只通过单一命令，所有入口复用。
7. 测试接线：除定向单测外，补接线测试或真机场景；纯函数单测不算入口已验证。
8. 汇报要包含矩阵覆盖：已验证哪些入口/状态、哪些没验。
9. 大功能：先交开源调研简报（2–4 个候选、近期活跃度、许可证、可借鉴业务逻辑/避免项、来源链接和日期）；不要凭印象推荐库或方案。
10. 场景与完成定义：先交本次改动的场景清单（按改动范围：小修 1–2 条，常规功能黄金路径 + 异常，新功能入口 × 状态矩阵；不抄固定清单）。除定向单测和接线测试外，从用户真实入口走这些场景；有定时器、周期刷新、文件监视或同步盘的功能做 10–15 分钟 soak。汇报里列未验证组合，不能用测试数量代替用户可用结果。

工作方式：
- 先创建 worktree：git worktree add -b qoder/<slug> "<worktrees-root>/<slug>/<repo>" main
- 之后所有工作都在该 worktree；不要启动或强关用户正在用的预览窗口。
- 完成后在该 worktree 本地提交（不 push、不合并 main）。

汇报（最终消息）：worktree、分支、commit SHA、改动文件、测试命令与结果、未验证项。不要贴大段 diff。
```

大功能或方向不确定时，把第一轮改成只读调研，要求交付：

```text
第一阶段只做只读调研并给出模型、开源调研与实现方案，不改代码。方案必须包含：入口清单、状态矩阵、不变量、候选对比与推荐（大功能）、推荐方案 / 改动文件与改动点 / 代价与风险 / 验收建议（黄金路径 + 边界 + 未验证项）。主控转交用户批准后再实现。
```

## 2.1 模型门槛 prompt（完整门槛时）

开工前给用户确认，或作为只读第一阶段的产出：

```text
模型（完整门槛）：
- 入口清单：<用户能到达该功能的全部路径，含修饰键/中键/右键/快捷键/拖拽/重启恢复>
- 状态矩阵：<入口 × 当前状态（文档/画板/文件夹/草稿/功能页/锁定）× 修饰键 × 是否跨重启>
- 不变量：<有活动文档就一定有对应标签；替换前先保存；会话从同一模型派生 …>
- 单一命令：<replace/new/beside 的入口函数，所有入口复用>
- 异常态：<空/加载/保存失败/外部修改/权限/缺失目标>
- 已拍板 / 未确认：<未确认项不实现>
```

完整模板见 [model-first.md](model-first.md)。

## 2.2 开源调研 prompt（大功能）

```text
大功能先做开源调研，不改代码。自主找 2–4 个近期活跃的候选（本地参考仓库 + GitHub + 官方文档），比较数据模型/交互/持久化/撤销/协作/许可证；技术栈不同就提炼业务逻辑和状态模型，不硬搬代码。输出：
- 候选对比表（链接、最近提交/release、许可证、技术栈、功能覆盖）
- 推荐：自研 / 借鉴 / 引入依赖，理由与代价
- 可借鉴 / 不借鉴清单
- 许可证与依赖风险
- 来源链接 + 查看日期；网络不可用时说明
调研简报经用户批准后再进入实现。
```

完整模板见 [open-source-research.md](open-source-research.md)。

## 3. Review follow-up 模板

先定档（见 [review-depth.md](review-depth.md)）：L1 1 个 reviewer；L2 1–2 个；L3 2–4 个，范围不重叠。在开发会话完成回调之后、合并之前发送；必须在**同一个会话窗口**里启动这些新 agent。

```text
主控流程要求：本批 review 档位 <L1/L2/L3>，在对话窗口里启动 <N> 个独立 review agent（并行），只读审查 worktree <worktree-path> 的 `git diff main...HEAD`，不能由开发会话自审。

每个 agent 只负责一个范围，不重复全量审：
1. <scope A>：<具体检查点>
2. <scope B>：<具体检查点>
3. <scope C>：<仅 L3/按需>

共用审查点：需求符合度、真实缺陷与遗漏、数据安全、模型/入口覆盖、测试与接线、未覆盖组合；不做风格挑刺。结论按 P1/P2 列出，带文件:行；L3 必须所有范围返回。每个 reviewer 必须写明“我实际运行/查看了什么”；UI/交互范围必须看真实窗口或主控提供的截图/录屏并对照原型，只读 diff 不能给 UI 通过。review 通过不等于功能验收。

拿到结论后：开发会话汇总去重，确认成立的 P1/P2 修复并新增 commit（不 amend、不 push），重跑受影响测试，再汇报 review 发现、已修项、修复 commit SHA、剩余问题；无缺陷也明确说明。修复前先归类（规则变更/未枚举组合/隐式状态/验证缺口），commit 带对应测试或文档更新，不能只打补丁。
```

已经合并的分支也补发同样的 review；有修复时再合并一次。

## 4. 合并与清理清单

```sh
# 1. 确认分支已合并且工作区干净
git -C "<worktree-path>" status --porcelain
git branch --merged main | cat

# 2. main 前进过则先 rebase，再快进合并
git -C "<worktree-path>" rebase main
git merge --ff-only qoder/<slug>

# 3. 该代码状态跑一次完整检查（有则跑）
scripts/check.sh

# 4. 删除已合并的 worktree 和分支
git worktree remove "<worktree-path>"
git branch -d qoder/<slug>

# 5. 推送前确认：主工作区干净、只剩主 worktree、无遗留已合并分支
git status --porcelain
git worktree list
git branch --merged main | cat

# 6. 推送前先问用户；得到明确同意后再执行
git push origin main
```

只删除确认已并入 main 且干净的；保留正在开发的；其他工具遗留的 detached worktree 未经用户确认不要删。合并和清理可以按流程做，但 **push 和归档会话前必须单独询问用户**。

推送 GitHub 前必须完成清理：`git status --porcelain` 为空、`git worktree list` 只剩主工作区、`git branch --merged main` 没有遗留的 `qoder/*` 分支。还有未合并/正在开发的 worktree 时保留它们，但不在该状态下推送，先把保留清单汇报给用户。只从主工作区推送 main。

## 5. UI 验收（平台电脑控制）

UI 改动交付前，用平台自带的电脑控制实际运行并操作软件：

- 使用 computer-use skill（宿主 Node REPL + Computer Use SDK）打开、点击、输入、截图。
- 从用户真实入口走：侧栏、主页、搜索、文档内引用、画板卡、重启恢复；不要用内部脚本命令代替入口。
- 先按模型列黄金路径和边界组合（锁定、功能页、草稿、重启恢复、保存失败），逐条操作并截图。
- UI 对照已通过的原型：位置、尺寸、出现/隐藏时机、空态、错误态、减少动态；没有原型时对照现有实现或参考软件。
- 有定时器、周期刷新、文件监视或同步盘的功能，连续操作 10–15 分钟，并模拟文件瞬时移走/只读/冲突副本。
- 截图保存成文件（PNG），在汇报里给绝对路径。
- 查看有代表性的真实画面；不要用“截图文件生成”或“测试通过”代替体验判断。
- 用户报告的手感/布局问题按 P1 验收缺口处理，补矩阵和 E2E。
- 单测/clippy 不能证明入口接线正确；没跑的组合要在汇报里列明。
- 不强关用户正在使用的窗口；不改用户数据；测试文档库按仓库 AGENTS 的规则使用隔离临时库或试用库副本。

## 6. 独立验收 prompt（acceptance agent）

主控已定本次改动范围：<小修/常规功能/新功能/高风险>。你是独立 acceptance agent，只读用户可见变更、原型/契约和模型，不先读实现，也不看开发会话的场景清单。

任务：在真实窗口/真实 CLI 上设计并执行场景。场景数量按改动范围：小修只覆盖改动入口/状态 + 一个直接回归；常规功能黄金路径 + 异常；新功能覆盖入口 × 状态矩阵；高风险加数据断言、重启和 soak/同步盘。你可以加对抗场景。

每个场景输出：ID、入口、真实手势、预期可见结果、数据断言、实际结果、证据 PNG 绝对路径、PASS/FAIL。必须写“我实际运行/查看了什么”。不能用 `pdf-annotate`、直接调 Workspace 方法或脚本截图代替用户手势。P1 失败阻断合并。
